# Maintainer Desk: security advisories that answer back

## Inspiration

I study software supply chain security, and the same moment keeps coming up. A scanner flags a
dependency, and the developer has one question: does this actually affect my app? OSV and GitHub
advisories answer half of it, which versions are vulnerable. What they leave out, under which
conditions the bug can be reached, lives in the maintainers' heads. It reaches users as a flood of "is this
project affected by CVE-X?" issues, written to volunteers who have no time to answer them.

An open agentic website has the right shape for this. A maintainer can publish an agent on the
project's own domain, the answer is attributable to that origin, and the visitor pays for the model
calls, not the volunteer.

## What it does

Maintainer Desk has two sides.

A **maintainer desk** is a small static website a project hosts next to its docs. It shows the
security policy, supported versions, each advisory with when it applies and when it does not,
workarounds, and a private report form. It publishes an agent network that answers "does this
apply to my setup?" from the maintainers' own notes, and an OSV feed for tools. The two demo desks,
for the fictional packages `lanternmd` and `tidecache`, were generated by the Desk Kit.

The **Triage Desk** is where a developer goes with a scanner alert. Paste `package.json`,
`package-lock.json` or `requirements.txt`. The page asks OSV.dev which advisories affect each exact
version (real data), reads the desk's own feed for packages that publish one, and sorts the
findings by CVSS score. Then ask the assistant: "We render lanternmd only from our own authors'
posts, with html off. Does LANTERN-2026-0001 apply?" The assistant reads the findings, and, after a
consent card that names the desk's origin, loads the maintainers' desk network into your browser
and asks it. It proposes an OpenVEX decision that cites the desk as its source. Nothing is recorded
until you press Apply, and the decisions download as an OpenVEX file that existing tools read.

For other builders there is the **Desk Kit** (a page and a command line tool that turn a
`desk.json` into a complete conforming desk, as a zip) and a **Spec Checks** page that runs the
spec's interoperability checks in the browser.

## How we built it

Plain HTML, CSS and ES modules, no framework, no server, no third-party scripts. Each site is a
static bundle with the challenge's browser runtime, a HOCON network and its resolved JSON, an
`agent-manifest.json`, `links.json`, discovery files and the action bridge, all checked with the
challenge's own `build_network.mjs --check` and `check_partner.mjs`.

One constraint of the spec shaped the design. A network called from another site gets only the
request text: no chat history, no private context, and none of either site's website tools. A desk
that only pointed callers to its page would be useless, so the kit writes the maintainers' notes
into a second agent, `advisory_notes`, generated from the same `desk.json` the page renders. A
caller gets grounded answers without site tools, and the notes cannot drift from the page.

Security choices, since that is the point of the project:

- The Triage Desk's only write action stages a proposal. The reference runtime runs write actions
  without a dialog; the spec asks to show the user the arguments first, so the visitor applies or
  discards every proposal on the page.
- A desk's answer is treated as data. The page refuses to cite a desk that was not contacted in the
  session, and labels each statement with its source origin.
- The page lists every origin it or its assistant contacted, and why.
- OSV.dev receives package names and versions only. Desk requests carry a package, a version, an
  advisory id and a usage question, never names or code.

## Challenges we ran into

Testing the cross-site call without a paid key. I ran it on a free local model through LM Studio
and a small CORS proxy. The first runs ended in empty answers. The request log showed the cause: the
model server ran out of context and sent an error event, and the runtime's stream parser skips
events it does not expect, so the failure never reached the screen. With a larger context the full
flow worked: consent card, the desk's agents running in the caller's browser on the caller's
router, a staged VEX proposal. The desk server logged no Authorization header at all.

## Accomplishments that we're proud of

- The full section 6 list is demonstrated: two-agent networks on a static host, site actions,
  loading an exact named network from a second origin after approval, the key never reaching the
  peer, private context filtered, and visible errors for an invalid network, a cycle, a budget and
  a denied origin.
- The Desk Kit's browser build is byte for byte the same as the command line build, and the zip it
  produces is checked in the tests.
- 22 Node tests cover the parsers, OSV range matching, CVSS scoring, OpenVEX rules, both desk pages,
  the triage flow and the spec build checks.

## What we learned

A peer network is most useful when it carries published knowledge with a clear owner. Peers
cannot reach their own site's tools when someone else calls them, so design for that from the
start. And the "visitor pays for inference" principle matters most for exactly the people who
cannot pay: volunteer maintainers.

## What's next

- Reading CycloneDX and SPDX SBOMs, not only lockfiles.
