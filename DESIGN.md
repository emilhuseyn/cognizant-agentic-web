# Maintainer Desk: DESIGN

Entry for the Cognizant Open Agentic Web Challenge (Devpost). Deadline 11 Jan 2027 08:00 PST (20:00 Baku).
Spec read: `cognizant-ai-labs/agentic-web` at commit `63a956c` (MVP Profile 0.2, spec file last changed
10 Nov 2026, so it is the version "as of the start of the Submission Period", 11 Nov). Written 16 Nov 2026.

## 1. The idea in one paragraph

Every scanner alert ends with the same question: "am I actually affected?" Databases (OSV, GitHub
advisories) say which versions are vulnerable, but not under which conditions the bug is reachable,
whether a workaround exists, or whether the maintainers plan a backport. That knowledge sits in
maintainers' heads, and it reaches users as a flood of "is this project affected by CVE-X?" issues.
**Maintainer Desk** is `security.txt` that answers questions: a maintainer publishes a small static
agentic website (a "desk") on the project's own origin. Its agent network carries the project's
security policy, advisories and applicability notes. A downstream developer's **Triage Desk** reads
their dependency list, pulls advisories from OSV.dev, and, for dependencies that publish a desk, asks
the maintainers' own agent (after a consent card that names the maintainer's origin) whether the
finding applies to how they use the package. Each decision is recorded as an OpenVEX statement that
cites its source: OSV.dev, or the maintainer's origin. The maintainer runs no server and pays for no
model calls (the spec's BYOK principle is exactly what unpaid open source maintainers need), and any
other agentic website (a coding helper, a docs site) can call the same desk.

## 3. What the spec lets a peer do (and why the design looks like this)

From the spec (§3.2) and the reference runtime (`runtime/runner.js`, `buildToolTable`):
- A peer network runs in the caller's browser, on the caller's router and key, with **only the request
  text**: no chat history, no `sly_data`, and **no `website_*` tools of either site**.
- So a peer answers from its published instructions (and optional MCP or coded tools). That makes a
  peer a carrier of *published knowledge*, attributed to its origin. A maintainer's applicability notes
  are exactly that kind of knowledge, and they are public by nature.
- Consequence for the desk: its network has a front agent (uses `website_*` tools on its own page) and
  an `advisory_notes` agent whose instructions are **generated by the kit from the same advisories file
  the page renders**, so a remote caller gets grounded answers without site tools and without drift.

## 4. Sites and networks

Three origins in the live demo (hosting to confirm with Emil, see §8):

| Site | Who it is for | Network (front agent) | Agents |
|---|---|---|---|
| Triage Desk | developer with a dependency list | `triage_desk` (`triage_desk`) | front + `vex_analyst` |
| lanternmd desk (demo) | users of a fictional npm markdown renderer | `lanternmd_security_desk` | front + `advisory_notes` |
| tidecache desk (demo) | users of a fictional PyPI HTTP cache | `tidecache_security_desk` | front + `advisory_notes` |
| Desk Kit (page on the Triage origin + Node script) | maintainers | none (a generator) | - |

`lanternmd` and `tidecache` were checked free on npm and PyPI on 16 Nov (`quillmark` was taken on PyPI,
dropped). Every page labels them as fictional demo projects.

### Triage Desk (main product)

Page: paste `package.json`, `package-lock.json` or `requirements.txt` (or load the demo app). The page:
1. parses the list (pinned versions; ranges are resolved only for lockfiles, otherwise flagged),
2. queries `https://api.osv.dev/v1/querybatch` and `/v1/vulns/{id}` (CORS verified 16 Nov),
3. for packages listed in its desk directory, reads the desk's static `osv/` feed (OSV schema, CORS),
4. shows a findings table: package, version, advisory, severity, fixed in, source, VEX status,
5. keeps a VEX ledger and exports an OpenVEX JSON document (download, client side),
6. shows a "Contacted origins" panel (spec §5 "Observable execution").

Site actions (`website_*`):

| Action | Effect | Does |
|---|---|---|
| `get_findings` | read | dependency list, findings, ledger, version counter, desk directory |
| `get_advisory` | read | OSV record details for one advisory id already in the findings |
| `propose_vex_statement` | write (staged) | stages a statement (status, justification, impact note, source) in the page; **the visitor applies or discards it with a button**. Nothing enters the ledger until they do. |

Why staged: spec §3.1 says the runtime MUST show the user the destination and arguments before a write.
The reference runtime runs `write` actions without a dialog (the skill lists this as a known gap). We
close it in the site: the model can only propose; the visitor commits.

Partners: each demo desk's network URL is a tool of `triage_desk`, its origin is in `allowed_peers`,
`peer_policy.mode` is `closed`, and `link_labels` names it ("lanternmd maintainers"). Request rule:
package, version, advisory id and a one-line usage question, under 140 characters, never names,
emails, repository URLs or code.

`vex_analyst` (separate knowledge): OpenVEX status and justification vocabulary, how to read a CVSS
vector, how to turn a maintainer's answer into a justification. It returns a proposed statement as
text; only the front agent calls `website_propose_vex_statement`.

### Maintainer desk (generated by the kit)

Page: project name, supported versions, how to report privately, advisories with affected ranges,
fixed versions, conditions, workarounds, and a "report a vulnerability" form that only opens an email
draft (the visitor sends it).

Site actions: `get_security_policy` (read), `check_version` (read: which advisories affect a version,
using the page's own semver range code), `get_advisory` (read), `draft_private_report` (write: fills the
page's report form; sending stays a visitor click in their mail client).

Published files: `agent-manifest.json`, `<network>.network.json`, `links.json`, `agent-mcp.json`,
`.well-known/nsdeploy.json`, `.well-known/nsdeploy-agent.json`, `bridge/`, `runtime/`, `osv/index.json`
and one OSV JSON per advisory.

### Desk Kit (community tooling, Potential Impact)

`kit/build_desk.mjs advisories/ security.json --out site/` turns OSV-format advisories plus a small
policy file into a conforming desk site: page, actions, HOCON, resolved network JSON (built with the
runtime's own parser and validator), manifest, discovery files and headers files for Netlify/Cloudflare
and Vercel. A browser version on the Triage origin does the same from a form and downloads a zip (no
install). Both demo desks are produced by the kit, which is the proof that it works.

Stretch (only if time allows): a coded-tool bundle with an SRI digest for `check_version`, so remote
callers get a deterministic version check (spec §3.3 optional coded tools). Needs the caller to serve
`runtime/sandbox-worker.js` with the CSP; GitHub Pages cannot, so it stays optional.

## 5. Stage-one conformance checklist (pass/fail, from the Official Rules and the spec)

Devpost Submission Requirements, verbatim items:
- [ ] Public URL of the open agentic website.
- [ ] "a publicly accessible conforming `.json` file that describes an agent network and its
      capabilities": `triage_desk.network.json`, and each desk's, at the manifest's `hocon` path.
- [ ] "a `runtime` file that can run the agent network in the browser": `runtime/` (the skill's patched
      nsdeploy runtime, unchanged, Apache 2.0 notice kept).
- [ ] "an interface that allows users or agents to interact with the agent network": chat panel on each
      page, plus the bridge for calling sites.
- [ ] "an optional interface that allows users to configure LLMs and keys": the runtime's
      "AI model settings" panel (BYOK).
- [ ] "the agent network should be able to interact with the website, optionally with other agentic
      websites, and/or be called by other agentic websites": `website_*` actions on every site; the
      Triage Desk calls the desks; every site keeps `{peer_rules}` and `bridge/` so others can call it.
- [ ] Text description; video under 2 minutes with browser footage and Emil explaining, public on
      YouTube, no third-party logos or music; one or more screenshots; Otari email and one problem
      sentence if we use Otari.

Spec (MVP Profile 0.2) MUSTs that a judge can check from outside:
- [ ] §2 Network is resolved, data-only JSON in the Neuro SAN model: metadata.description, a front agent,
      unique agent names, function descriptions with JSON Schema `parameters`, instructions, `tools`;
      no includes, substitutions or publisher-only paths; no `demo_mode`; no Python/`class`/toolbox tools.
- [ ] §2.1 Private context deny-by-default: no `allow` blocks forwarding `sly_data` to peers.
- [ ] §3.2.1 Network URL = folder holding `agent-manifest.json` + exact network name; manifest name
      matches the file name and the `.hocon` name; caller refuses any other name.
- [ ] §3.3 `agent-manifest.json` has `networks[]` with `name`, `front_man`, `hocon`; `llm_router`;
      `allowed_peers` + `peer_policy` (`closed`); `deployment.mode: static`; served with
      `Access-Control-Allow-Origin: *` (GitHub Pages sends it on every file; Vercel/Netlify via config).
- [ ] §3.3 `links.json` published (`version: 1`).
- [ ] §3.2.4 / §5 Consent card before each cross-origin peer contact, naming origin and request.
- [ ] §3.4 / §4 BYOK key stays in the browser, goes only to the selected router, never to a peer, never
      in URLs, manifests, prompts, traces; user can delete the stored profile.
- [ ] §3.1 Runtime validates the network before any model call; bounded execution (runtime limits: 4
      partner calls, 24 agent calls, 90 s per message, depth 5).
- [ ] §3.1 Writes shown before they happen (our staged `propose_vex_statement`; desk's
      `draft_private_report` only fills a form).
- [ ] §5 Peer answers treated as data: the Triage Desk never lets a desk answer trigger an action, and
      labels every statement with its source origin.
- [ ] Production over HTTPS.

Spec §6 interoperability checks we will demonstrate (most entries will not):
- [ ] two-agent network published from an ordinary HTTPS host (each site has two agents);
- [ ] runs with the site's default router and with a user-selected one (BYOK);
- [ ] internal agent call + grounded capability through a registered site action;
- [ ] after approval, load an exact named network from a second origin and run it locally;
- [ ] the second site never receives the key and cannot change the router (show the desk server log
      or the Network panel: no Authorization header, no key);
- [ ] private context absent at the peer;
- [ ] visible errors for an invalid network, a cycle, an over-budget request and a denied origin
      (a "Spec checks" page on the Triage origin that triggers each one with fixtures).

Build checks before every push: `build_network.mjs --check`, `node --test`, `check_partner.mjs` on each
desk URL with the Triage origin, and on the Triage URL with no origin.

## 6. Judging criteria, how this answers each

- Technological Implementation: three conforming sites on three origins, real OSV data, staged writes,
  consent, BYOK isolation shown, the §6 checks page, Node tests, a generator built on the runtime's own
  parser and validator.
- Design: one coherent job (triage a dependency list to a VEX file), a findings table that works
  without any key, the assistant as a helper, not the whole UI.
- Potential Impact: real audience on both sides (developers drowning in scanner alerts; maintainers
  flooded with "am I affected" issues), zero hosting and model cost for maintainers, an open kit
  anyone can run, OpenVEX output that existing tools read.
- Quality of the Idea: a peer network as an origin-attributed authority, not a shop; the knowledge
  that databases lack (conditions, workarounds) is exactly what a published network can carry.
  Emil's research is software supply-chain security measurement, which is the problem space.

## 7. Stack and rules

Plain HTML, CSS and ES modules, no framework, no build step for the pages, no third-party scripts
(spec §4 threat boundary). Node 22 only for the kit, the build check and tests. Default router: hosted
Otari with `alibaba/qwen3.8-flash`, as in the skill template; any OpenAI-compatible router with CORS works
through BYOK. Nothing we run is paid. Commits carry Emil Huseynov's identity only. AI coding assistance
is disclosed in the Devpost text.
